1. ARCHITECTURE GÉNÉRALE
================================================================================

Stack Technique
---------------
- Frontend  : Angular 17 (standalone components, signaux réactifs)
- Backend   : Spring Boot 3 + Spring Security + JWT
- Base de données : MongoDB (NoSQL)
- Paiement  : FedaPay (agrégateur MTN MoMo / Moov / Celtiis)

Frontend (Angular) <-> Backend (Spring Boot REST) <-> MongoDB

WebSocket             : /ws/ (notifications temps réel, stocks)

3. FLUX D'INSCRIPTION — CLIENT (étapes exactes)
================================================================================

/auth/register
  → Choisir profil: CLIENT
  → état: role = CLIENT

/auth/register/client
  → Choisir besoin: CONSULT ou LIVRAISON
  → état: clientNeed

/auth/register/client/plans
  → Lister plans (type = CLIENT_CONSULT ou CLIENT_LIVRAISON)
  → Choisir un plan payant
  → état: selectedPlan

/auth/register/form  (guards: inscriptionGuard + inscriptionPlanGuard)
  Étape 1 — Nom complet
  Étape 2 — Téléphone
    POST /api/v1/auth/otp/envoyer
      → CPassOtpService.sendOtp(phone)
      → CpassOtpRef créée en BD (referenceId + expiresAt)
      → SMS envoyé au téléphone
    Saisir code OTP reçu
    POST /api/v1/auth/register
      → OtpFacade.confirmOtp() — vérifie code avec CPass API
      → User créé (telephoneVerifie = true, password = UUID aléatoire)
      → SubscriptionService.subscribe(planCode)
        → Subscription créée (statut = PENDING)
        → FedaPayService.creerTransaction()
        → Retourner checkoutUrl FedaPay

Paiement FedaPay (MTN / Moov / Celtiis)

Webhook FedaPay → POST /api/v1/paiement/webhook
  → Signature HMAC-SHA256 vérifiée
  → SubscriptionService.activateSubscription()
    → Subscription.statut = ACTIVE
    → dateDebut = maintenant, dateFin = maintenant + plan.dureeJours
    → quotaRestant = plan.quota

/paiement/confirmation
  → Polling statut (toutes les 2.5s, max 6 fois)
  → Afficher résultat (succès / en attente / échec)

5. SYSTÈME D'ABONNEMENT (Subscription)
================================================================================

Modèle SubscriptionPlan
------------------------
  type         PlanType (REVENDEUR | CLIENT_CONSULT | CLIENT_LIVRAISON)
  nom, code    identifiants
  prix         int (FCFA)
  dureeJours   int
  quota        int (-1 = illimité, sinon nombre de consultations/livraisons)
  actif        boolean (désactivable par admin)
  recommande   boolean (badge "Recommandé" sur UI)
  ordre        int (tri dans l'affichage)

Modèle Subscription
--------------------
  userId       String (indexed)
  planId/Code/Type
  dateDebut, dateFin (indexed)
  quotaRestant int
  statut       PENDING | ACTIVE | EXPIRED
  transactionId (lien FedaPay)

Cycle de vie d'un abonnement
-----------------------------
  PENDING  → créé lors de subscribe(), avant paiement
  ACTIVE   → activé par webhook FedaPay (activateSubscription())
  EXPIRED  → passé par scheduler quotidien à 02h00 UTC

Renouvellement
--------------
  Si abonnement actif du même type existe:
    → ancienne.statut = EXPIRED
    → nouvelle.dateDebut = ancienne.dateFin (pas de "trous")

Quota décrémenté
----------------
  À chaque consultation connectée : SubscriptionService.decrementQuota(userId, CLIENT_CONSULT)
  À chaque commande livraison     : SubscriptionService.decrementQuota(userId, CLIENT_LIVRAISON)
  Jamais réinitialisé automatiquement — rechargé uniquement à l'activation d'un nouveau plan.

Expiration (scheduler)
-----------------------
  AbonnementScheduler.java
  @Scheduled "0 0 2 * * *" (02h00 UTC chaque jour)
    → subscriptionService.checkExpirations()
       → Subscription ACTIVE où dateFin < now → statut = EXPIRED

  @Scheduled "0 0 9 * * *" (09h00 UTC chaque jour)
    → subscriptionService.getExpiringWithin(7)
       → Notification in-app "Votre abonnement expire dans N jour(s)"

Dual system (legacy)
--------------------
  Ancien : Revendeur.abonnement (enum: GRATUIT / TEST / MENSUEL / TRIMESTRIEL / SEMESTRIEL / ANNUEL)
  Nouveau: Subscription (flexible)
  Sync   : mapLegacyAbonnement(planCode, dateFin) — mapping par substring (voir LIMITATION #1)

6. SYSTÈME DE CONSULTATION FREEMIUM
================================================================================

VISITEUR ANONYME
----------------
Limite : 3 consultations gratuites (ConsultationSession.LIMITE_GRATUITE = 3)

Identifiant : UUID fingerprint stocké dans localStorage (clé: 'gf_fp')
Fallback    : IP (X-Forwarded-For → X-Real-IP → RemoteAddr)

Flux:
  Clic "Commander" dans RevendeurCardComponent
    → consultationService.consulter() (anonyme uniquement)
      → POST /api/v1/consultations/consulter?fingerprint=UUID
        → ConsultationService.verifierEtIncrementer(fingerprint, ip)
           1. Chercher ConsultationSession par fingerprint
           2. Si nouveau fingerprint + IP a déjà limite → bloquer (voir BUG #1)
           3. Si nombreConsultations >= 3 → retourner autorise=false
           4. Sinon nombreConsultations++ + save
           → Retourner ConsultationDTO(autorise, restantes, limite)
    → Si !autorise → afficher ConsultationPaywallComponent
      "Quota épuisé — Créer un compte gratuit"

Cache local: statut stocké dans localStorage (clé: 'gf_quota') pour éviter le flash

UTILISATEUR CONNECTÉ
---------------------
  Dans RevendeurCardComponent.onCommander():
    if (authService.estConnecte()) {
      this.commander.emit(revendeur);  ← BYPASS TOTAL du quota
      return;
    }

  → Les connectés ne passent PAS par consulterAuth()
  → Accès illimité pour tout compte créé, même sans abonnement actif

  IMPORTANT: Le backend a la logique consulterAuth() avec décrémentation du quotaRestant,
             mais le frontend ne l'appelle jamais lors d'un clic "Commander".
             Cela signifie qu'un compte créé gratuitement a accès illimité.

  → Voir BUG #2 (critique)

7. SYSTÈME OTP (CPass)
================================================================================

Configuration
-------------
  baseUrl      : https://api-gateway.clubchretien.org/cc-cpass
  client_id    : [REDACTED — variable d'env CPASS_CLIENT_ID]
  client_secret: [REDACTED — variable d'env CPASS_CLIENT_SECRET]
  Auth         : POST /auth/token → access_token (Bearer, expire 1h)
  Refresh      : POST /auth/refresh → nouveau token automatique

Endpoints CPass utilisés
------------------------
  POST /otp/send   body: {"to": "+2290XXXXXXXXX"}
    → Réponse: {"referenceId": "uuid", "expiresAt": "..."}

  POST /otp/verify body: {"referenceId": "uuid", "otpCode": "123456"}
    → Réponse: {"verified": true/false, "attemptsRemaining": N}

Modèle CpassOtpRef (MongoDB)
-----------------------------
  phoneNumber  (local, sans +229)
  referenceId  (UUID CPass)
  expiresAt    (Instant)
  used         (boolean, marqué true après vérification)
  createdAt

Flux complet
------------
  1. POST /api/v1/auth/otp/envoyer (téléphone)
     → OtpFacade.initOtp()
       → PhoneNumberService.normaliserTelephoneInternational()
       → CPassOtpService.sendOtp(phoneInternational)
       → Supprimer anciens OTP non utilisés pour ce numéro
       → CpassOtpRef créée + sauvegardée

  2. POST /api/v1/auth/otp/verifier ou inclus dans /auth/register
     → OtpFacade.confirmOtp(telephone, code)
       → Chercher CpassOtpRef non-utilisée la plus récente
       → Vérifier expiresAt
       → CPassOtpService.verifyOtp(referenceId, code)
       → Si verified: CpassOtpRef.used = true

Gestion token CPass (CPassTokenService)
----------------------------------------
  Cache en mémoire (ConcurrentHashMap + ReentrantLock)
  Refresh automatique 60s avant expiration
  Si 401 sur /otp/send → refresh silencieux + retry 1x

Exceptions
----------
  OtpExpiredException   "Le code OTP a expiré"
  OtpInvalidException   "Code OTP invalide"
  OtpProviderException  "Le fournisseur OTP a échoué"

8. PAIEMENT FEDAPAY
================================================================================

Configuration
-------------
  baseUrl    : https://api.fedapay.com/v1
  checkoutUrl: https://process.fedapay.com
  webhookSecret: HMAC-SHA256
  callbackUrl: https://gazfacile.netlify.app/paiement/confirmation

Flux complet
------------
  1. POST /api/v1/paiement/initier (authentifié)
     → FedaPayService.creerTransaction() → fedaPayId (numérique)
     → FedaPayService.obtenirToken(fedaPayId) → token paiement
     → URL checkout: https://process.fedapay.com/{token}
     → Transaction créée en BD (statut = PENDING)
     → Retourner checkoutUrl au frontend

  2. Client paie sur FedaPay (MTN / Moov / Celtiis)

  3. Webhook FedaPay → POST /api/v1/paiement/webhook
     → Vérifier signature x-fedapay-signature (HMAC-SHA256)
     → PaiementService.traiterWebhook(fedaPayId, "approved")
       → Transaction.statut = APPROVED
       → Si ABONNEMENT: SubscriptionService.activateSubscription()
       → Si COMMANDE: Commande.statutPaiement = PAYE
     → Retourner 200 OK toujours (éviter retry infini)

  4. /paiement/confirmation?reference=REF&status=approved
     → Polling GET /api/v1/paiement/transaction/{reference}
     → Toutes les 2.5s, max 6 tentatives
     → Afficher résultat

Statuts Transaction
-------------------
  PENDING   → créée, en attente paiement
  APPROVED  → paiement validé
  DECLINED  → refusé
  CANCELLED → annulé par client
  REFUNDED  → remboursé (non géré côté app)
  TRANSFERRED → versé au commerçant

Types Transaction
-----------------
  ABONNEMENT (lié à subscriptionId)
  COMMANDE   (lié à commandeId)

9. GESTION DES COMMANDES
================================================================================

Modèle Commande (champs clés)
------------------------------
  revendeurId, revendeurNom
  clientTelephone, clientAdresseLivraison, clientLocation [lon, lat]
  marque       (enum MarqueGaz: BENIN_PETRO | ORYX | PROGAZ | JNP | AUTRE)
  taille       (enum FormatBouteille: KG_3 | KG_6 | KG_12 | KG_25 | KG_38)
  quantite, prixUnitaire, total
  distanceKm, fraisSupplementaires
  modePaiement (MOBILE_MONEY | VIREMENT_BANCAIRE | ESPECES)
  statutPaiement (EN_ATTENTE | PAYE | REMBOURSÉE)
  statutCommande (EN_ATTENTE | CONFIRMÉE | LIVRÉE | ANNULÉE)
  livreurAssigne (String, non utilisé)
  livraisonAt   (Instant, défini quand LIVRÉE)

Calcul tarif
------------
  RAYON_GRATUIT = 5 km
  Si distance > 5 km: fraisSupplementaires = (distance - 5) * 200 FCFA/km
  total = (prixUnitaire * quantite) + fraisSupplementaires
  Distance calculée par formule Haversine (lat/lon client vs revendeur)

Flux
----
  POST /api/v1/commandes
    → Vérifier disponibilité produit
    → Calculer distance + frais
    → Décrémenter quota CLIENT_LIVRAISON si abonnement actif
    → Commande créée (EN_ATTENTE / EN_ATTENTE paiement)

  PUT /api/v1/commandes/{id}/statut (revendeur)
    EN_ATTENTE → CONFIRMÉE → LIVRÉE
    Si LIVRÉE: livraisonAt = now + statutPaiement = PAYE

  Notifications créées à chaque changement statut

  Refresh token : 7 jours
  Intercepteur  : JwtInterceptor.ts ajoute "Authorization: Bearer ..."

-------------

  Backend  : POST /api/v1/auth/google {idToken, ...}
    → GoogleTokenService.valider(idToken) — vérifie signature JWT Google
    → Cas 1: googleId connu → login direct
    → Cas 2: email connu   → lier googleId
    → Cas 3: nouveau compte → téléphone obligatoire via Firebase Phone Auth
      → Réponse 428 PRECONDITION_REQUIRED si téléphone manquant
      → Frontend redemande tel + OTP Firebase
      → Réessayer avec firebaseIdToken

OTP Login (sans password)
--------------------------
  /auth/login → envoyer OTP → vérifier → JWT retourné
  Même flux que inscription sauf que User existe déjà

14. BUGS IDENTIFIÉS
================================================================================

BUG #1 — CRITIQUE: freemium ipAtteintLimite() non exhaustif
-------------------------------------------------------------
Fichier : ConsultationService.java, méthode ipAtteintLimite(), ligne ~159

Code actuel:
  consultationRepository.findByIpAddress(ip)  ← retourne Optional (UNE seule session)
  .map(s -> !s.getFingerprint().equals(fingerprintExclu)
          && s.getNombreConsultations() >= LIMITE_GRATUITE)
  .orElse(false)

Problème:
  Si plusieurs sessions existent pour la même IP, seulement la première retournée
  par MongoDB est vérifiée. Un attaquant peut vider son localStorage, obtenir un
  nouveau fingerprint et éventuellement contourner le blocage IP.

Correction:
  Utiliser findAllByIpAddress() (List) + .anyMatch(...)
  ou créer un index compound sur (ipAddress) avec compteur global

---

BUG #2 — CRITIQUE: connecté = accès illimité sans payer
---------------------------------------------------------
Fichier : revendeur-card.component.ts, méthode onCommander()

Code actuel:
  if (this.authService.estConnecte()) {
    this.commander.emit(this.revendeur);  ← pas de vérification quota
    return;
  }

Problème:
  Tout utilisateur connecté (même sans abonnement actif) a accès illimité.
  Le backend consulterAuth() décrémenterait le quota correctement,
  mais le frontend ne l'appelle jamais.

Impact:
  Le modèle économique est cassé — créer un compte gratuit = accès illimité.

Correction proposée:
  Appeler consultationService.consulter() (qui route vers consulterAuth si connecté)
  avant d'émettre commander.emit(), et afficher une paywall si !autorise.

15. LIMITATIONS / RISQUES
================================================================================

LIMITATION #1 — Dual system abonnement revendeur
-------------------------------------------------
  Deux systèmes coexistent:
    Ancien: Revendeur.abonnement (enum Abonnement)
    Nouveau: Subscription (collection MongoDB)

  La synchronisation repose sur mapLegacyAbonnement() qui fait du pattern matching
  par substring sur le planCode (ex: contains("PRO") → ANNUEL).
  Risque de désynchronisation si les codes de plans changent.

LIMITATION #2 — Pas de rate limiting sur /otp/envoyer
------------------------------------------------------
  Un attaquant peut déclencher des milliers de SMS en boucle.
  Chaque SMS coûte sur CPass.
  Aucun throttle, CAPTCHA ou délai minimum entre envois.

LIMITATION #3 — Idempotence webhook FedaPay faible
---------------------------------------------------
  Si FedaPay renvoie le webhook 2x (retry), activateSubscription() sera
  appelée deux fois. La 2e fois, l'ancienne (qui vient d'être EXPIRED)
  sera recréée avec dateFin doublée.
  Correction: vérifier Transaction.statut != APPROVED avant traitement.

LIMITATION #4 — Fingerprint localStorage effaçable
---------------------------------------------------
  Vider le localStorage suffit pour repartir de 0 côté quota anonyme.
  Combiné avec le bug #1, facile à contourner.
